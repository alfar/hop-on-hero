# Implementation Plan: Player Death Ends the Round with a Summary Screen

## Overview
Four pieces of work, roughly in dependency order: (1) give `Player` a death sequence mirroring `Enemy`'s existing stop/disable/animate pattern, but driven by a new `AnimationPlayer` clip instead of a hardcoded tween; (2) add round-end broadcasting and a `get_tree().paused` freeze; (3) build the first `Control`-based UI in this project, a plain `SummaryScreen` with a time-played label and two buttons; (4) wire a seed-carrying restart mechanism through `get_tree().reload_current_scene()`. Each piece is independently testable before the next depends on it, and the existing `Enemy` death-sequence tests (`test/integration/enemy/enemy_death_test.gd`) are the closest available precedent for structuring `Player`'s equivalent tests.

## Architecture Decisions
- `Player._on_died()` mirrors `Enemy._on_died()` for movement-stop (reusing `StayStillMovementBehavior`), but plays its fade via a new `AnimationPlayer` child + a "death" animation resource instead of `Enemy`'s hardcoded `create_tween()` call — per user request, so the death animation's content (fade timing, squash, rotation, whatever comes later) can be redesigned entirely in the editor without touching `player.gd`. `Player._on_died()` does `$AnimationPlayer.play("death")` then `await $AnimationPlayer.animation_finished`; the animation resource's own authored track length is the single source of truth for duration, so there is no separate `death_fade_duration`-style `@export` to keep in sync with it (unlike `Enemy.death_fade_duration`, which stays as-is — this feature does not touch `Enemy`). This is this project's first use of `AnimationPlayer` anywhere.
- `Player._on_died()` does **not** `queue_free()` — the player node must survive so `SummaryScreen`'s data (time played, and future stats) has something to still exist by the time it's read, and so `get_tree().paused` can freeze the player in place rather than removing it.
- `GameEvents.round_ended` is a **plain Godot `signal` on the `GameEvents` autoload, not a `BehaviorSubject`**, despite `docs/project.md`'s general convention that cross-cutting `GameEvents` state uses `BehaviorSubject`. Rationale: `BehaviorSubject.subscribe()` replays its last cached value immediately to every new subscriber (per `behavior_subject.gd:23-26`). `round_ended` is fired once per round and the *autoload survives* `get_tree().reload_current_scene()`, but nothing would naturally re-`emit()` a fresh "not ended" value on the next load the way `World._ready()` re-emits `world_size_changed`/`world_loaded` every load (`world.gd:6-8`) — so a `BehaviorSubject` here would incorrectly instantly re-fire "round ended" to the next round's fresh `game.gd` subscriber. A plain `signal`, connected fresh each `game.gd._ready()`, has no replay behavior and avoids this trap entirely. This deliberately deviates from the stated convention, with this rationale recorded for `/sdd-archive`.
- `GameEvents.next_level_seed` is a plain `var: int = 0` (not a `BehaviorSubject`, not a signal) — a one-shot carry-through value read once by `ActivityManager._ready()` on the next load, exactly as scoped in `feature.md` FR-05. No emission/subscription needed; it's just an autoload-scoped variable, which is the simplest thing that survives a scene reload.
- `ActivityManager._ready()` reads `GameEvents.next_level_seed` itself (rather than `Game` injecting it top-down) to sidestep Godot's bottom-up `_ready()` ordering — this was flagged as the simpler option in `feature.md` FR-05's Open Questions and is confirmed here as the approach: no ordering hazard, no new inter-node wiring needed.
- `SummaryScreen` follows the same "presentation scene reflects state, doesn't drive behavior" convention as `HealthBar`/`InventoryDisplay` — it exposes `show_summary(time_played_seconds)` and two signals (`retry_pressed`, `new_seed_pressed`); `game.gd` owns all restart/reload logic. This is this project's first `Control`-based scene, placed under `scenes/summary_screen/` per the existing `scenes/<name>/` convention for presentation scenes.
## Implementation Steps

### Step 1: `Player` death sequence
- [x] `scenes/player/player.tscn`: add an `AnimationPlayer` child node. Create a new `Animation` resource named `"death"` on it with a single track animating `Player:modulate:a` from `1.0` to `0.0` over a short duration (e.g. `0.2s`, matching `Enemy.death_fade_duration`'s current default — a reasonable starting point, freely re-editable later since it's now pure animation data, not code).
- [x] `scenes/player/player.gd`: add `@onready var _animation_player: AnimationPlayer = $AnimationPlayer`. In `_ready()`, add `$Status/HealthComponent.died.connect(_on_died)` (mirrors `enemy.gd:18`). Add `func _on_died() -> void:`:
  - `movement_behavior = StayStillMovementBehavior.new()` (stops movement immediately, same as `Enemy._on_died()`).
  - Stop `_timer_weapon_trigger` from firing — see Step 2 for the exact mechanism added to `TimerWeaponTrigger`.
  - `_animation_player.play("death"); await _animation_player.animation_finished`.
  - After the await, emit the round-end signal (`GameEvents.round_ended.emit(time_played_seconds)` — see Step 3 for where `time_played_seconds` comes from; `Player` reads it via a small helper rather than owning its own timer, to keep round-timing logic in one place).
  - Do **not** call `queue_free()`.
- Files: `scenes/player/player.tscn`, `scenes/player/player.gd`

### Step 2: Stop `TimerWeaponTrigger` from firing on death
- [x] `components/weapon/timer_weapon_trigger.gd`: add `func stop() -> void: _timer.stop()`, halting the existing `Timer` node so `_on_timeout()` can't fire again. `Player._on_died()` (Step 1) calls `_timer_weapon_trigger.stop()`. (An initial `set_process(false)` addition was removed post-review as dead code — this script has no `_process()` override.)
- Files: `components/weapon/timer_weapon_trigger.gd`

### Step 3: Round timer + `GameEvents.round_ended`
- [x] `components/events/game_events.gd`: add `signal round_ended(time_played_seconds: float)` as a plain signal (see Architecture Decisions for why not `BehaviorSubject`) and `var next_level_seed: int = 0`.
- [x] `scenes/game.gd`: add `var _round_start_ticks_msec: int` set in `_ready()` via `Time.get_ticks_msec()`. Add `func get_time_played_seconds() -> float: return (Time.get_ticks_msec() - _round_start_ticks_msec) / 1000.0`.
- [x] `scenes/player/player.gd`'s `_on_died()` (Step 1) needs a way to reach `Game.get_time_played_seconds()` without a hardcoded parent-type assumption that would break in isolated tests (where `Player` is instanced standalone, not under `Game` — see `weapon_test_helpers.gd`'s `make_player()` pattern). Use `get_tree().get_first_node_in_group("game")` (mirroring `TimerWeaponTrigger._find_nearest_enemy()`'s existing `get_tree().get_nodes_in_group("enemy")` pattern) — add `add_to_group("game")` to `Game._ready()`. If no `Game` node is found (standalone test instantiation), `_on_died()` passes `0.0` as the elapsed time rather than erroring, so `Player`'s own tests don't need a full `Game` scene just to exercise the death sequence.
- Files: `components/events/game_events.gd`, `scenes/game.gd`, `scenes/player/player.gd`

### Step 4: World freeze on round end
- [x] `scenes/game.gd`: in `_ready()`, add `add_to_group("game")` (Step 3) and `GameEvents.round_ended.connect(_on_round_ended)`. Add `func _on_round_ended(time_played_seconds: float) -> void: get_tree().paused = true; $HUD/SummaryScreen.show_summary(time_played_seconds)` (the `SummaryScreen` node itself is added in Step 5).
- Files: `scenes/game.gd`

### Step 5: `SummaryScreen` scene (first `Control`-based UI)
- [x] Create `scenes/summary_screen/summary_screen.gd`: `class_name SummaryScreen`, `extends Control`.
  - `signal retry_pressed`
  - `signal new_seed_pressed`
  - `@onready var time_label: Label = $TimeLabel`
  - `func _ready() -> void: visible = false; $RetryButton.pressed.connect(func(): retry_pressed.emit()); $NewSeedButton.pressed.connect(func(): new_seed_pressed.emit())`
  - `func show_summary(time_played_seconds: float) -> void:`
    - Format `mm:ss`: `var minutes := int(time_played_seconds) / 60; var seconds := int(time_played_seconds) % 60; time_label.text = "%02d:%02d" % [minutes, seconds]`
    - `visible = true`
- [x] Create `scenes/summary_screen/summary_screen.tscn`:
  - Root `Control` named `SummaryScreen`, script attached, `process_mode = 3` (`PROCESS_MODE_ALWAYS` — required so its buttons stay responsive after `get_tree().paused = true`, per `feature.md` FR-02), anchors set to full-rect (`anchor_right = 1.0`, `anchor_bottom = 1.0`) so it covers the viewport.
  - Child `Label` named `TimeLabel` (plain default styling, centered near the top).
  - Child `Button` named `RetryButton`, text `"Retry"`.
  - Child `Button` named `NewSeedButton`, text `"New Seed"`.
  - Simple vertical layout (e.g. a `VBoxContainer` wrapping the label and two buttons, centered) — no theme resource, default Godot look throughout, per `feature.md`'s explicit "no styling" scope.
- Files: `scenes/summary_screen/summary_screen.gd`, `scenes/summary_screen/summary_screen.tscn`

### Step 6: Wire `SummaryScreen` into `game.tscn` + restart logic
- [x] `scenes/game.tscn`: add a `SummaryScreen` node (instanced from `summary_screen.tscn`) as a child of the existing `HUD` `CanvasLayer`, alongside `InventoryDisplay`.
- [x] `scenes/game.gd`: in `_ready()`, connect `$HUD/SummaryScreen.retry_pressed` and `$HUD/SummaryScreen.new_seed_pressed`.
  - `func _on_retry_pressed() -> void: GameEvents.next_level_seed = $ActivityManager.level_seed; get_tree().paused = false; get_tree().reload_current_scene()`
  - `func _on_new_seed_pressed() -> void: GameEvents.next_level_seed = 0; get_tree().paused = false; get_tree().reload_current_scene()`
  - `get_tree().paused = false` is set explicitly **before** `reload_current_scene()` rather than assumed to reset automatically — this resolves `feature.md`'s Open Question conservatively (see Risks below for why this is safe either way).
- [x] `components/activities/activity_manager.gd`: in `_ready()`, before the existing `if level_seed == 0: level_seed = randi()` check, add `if GameEvents.next_level_seed != 0: level_seed = GameEvents.next_level_seed`. This makes "Retry" carry the exact previous seed through, and leaves "New Seed" (`next_level_seed = 0`) falling through to the existing randomize-on-zero behavior unchanged.
- Files: `scenes/game.tscn`, `scenes/game.gd`, `components/activities/activity_manager.gd`

### Step 7: Unit tests for pure-logic pieces
- [x] `test/unit/events/game_events_test.gd` (extend if a suitable file exists, else create): confirm `GameEvents.round_ended` is a plain signal (connecting and emitting synchronously delivers exactly once, with no replay-to-late-subscriber behavior) — a smoke test that would fail loudly if this were ever accidentally changed back to a `BehaviorSubject`.
- [x] `test/unit/activities/activity_manager_test.gd` (extend if exists, else create a minimal one): `ActivityManager._ready()` uses `GameEvents.next_level_seed` when non-zero, and falls back to randomize when it's `0` — test by setting `GameEvents.next_level_seed` before instancing/readying a bare `ActivityManager.new()` with `level_seed = 0` and asserting the resulting `level_seed`. Reset `GameEvents.next_level_seed = 0` at the end of each test (or in `after_each`) so this doesn't leak into other tests, since it's shared autoload state.
- Files: `test/unit/events/game_events_test.gd` (new or extended), `test/unit/activities/activity_manager_test.gd` (new or extended)

### Step 8: Integration tests for `Player` death sequence
- [x] `test/integration/player/player_death_test.gd` (new, mirroring `test/integration/enemy/enemy_death_test.gd`'s structure):
  - `test_died_stops_movement_immediately`: construct a standalone `Player` (via `WeaponTestHelpers.make_player()`), give it a moving `MovementBehavior`, emit `died` on its `HealthComponent`, assert velocity is zero before any `await` (mirrors `enemy_death_test.gd:8-23`'s same-frame assertion pattern).
  - `test_died_stops_weapon_firing`: emit `died`, call `$TimerWeaponTrigger._on_timeout()` directly afterward, assert no projectile spawns (proving `stop()` actually halted it, not just that the `Timer` node happens not to have elapsed yet).
  - `test_died_fades_out_but_does_not_free_the_player`: emit `died`, `await player._animation_player.animation_finished` (or `await wait_seconds(...)` covering the "death" animation's authored length plus a small margin, if awaiting the signal directly proves awkward inside a GUT test), assert `player.modulate.a == 0.0` **and** `is_instance_valid(player)` is still `true` and NOT queued for deletion (the key divergence from `Enemy`'s equivalent test).
  - `test_died_emits_round_ended_with_zero_time_when_no_game_node_exists`: emit `died` on a standalone `Player` (no `Game` ancestor), await the animation's completion, assert `GameEvents.round_ended` fired with `0.0` (proving the "no Game found" fallback from Step 3 works, without needing a full `Game` scene in this test file).
- Files: `test/integration/player/player_death_test.gd`

### Step 9: Integration tests for round-end flow via `game.tscn`
- [x] `test/integration/game/round_end_test.gd` (new):
  - `test_player_death_pauses_the_tree_and_shows_summary_screen`: instance `game.tscn` (mirroring `game_scene_wiring_test.gd`'s pattern), force the player's `HealthComponent.died` to emit, await the death animation's completion, assert `get_tree().paused == true` and `game.get_node("HUD/SummaryScreen").visible == true`.
  - `test_summary_screen_shows_correct_elapsed_time`: instance `game.tscn`, `await wait_seconds(...)` a known short duration before triggering death, assert the displayed `TimeLabel.text` matches the expected `mm:ss` (within the test's own tolerance for real-time drift, e.g. assert it's one of two adjacent acceptable values, since `Time.get_ticks_msec()` isn't perfectly deterministic against `wait_seconds`).
  - `test_retry_reloads_with_the_same_seed`: instance `game.tscn`, read `ActivityManager.level_seed` after initial `_ready()`, trigger death, press `RetryButton` (call `_on_retry_pressed()` directly — GUT's own docs already establish, per this project's existing `InventoryDropInput` tests, that headless input simulation is unreliable, so calling the handler directly is the established pragmatic substitute), reload, and assert the new instance's `ActivityManager.level_seed` equals the original. **Caveat**: `reload_current_scene()` reloads the actual running main scene tree, which under GUT's test runner is not straightforward to assert on directly (the test's own scene, not `game.tscn`, is the active "main" scene during a test run) — see Risks below; this test may need to call `_on_retry_pressed()`'s logic minus the actual `reload_current_scene()` call (i.e. assert `GameEvents.next_level_seed` was set correctly, and separately unit-test that `ActivityManager` honors it in Step 7) rather than a true end-to-end reload-and-reinspect. Finalize the exact assertion shape during implementation once GUT's reload behavior under test is confirmed.
  - `test_new_seed_sets_next_level_seed_to_zero`: same caveat — assert `GameEvents.next_level_seed == 0` after `_on_new_seed_pressed()`, rather than asserting on a live reloaded scene's resulting seed (already covered by Step 7's `ActivityManager` unit test).
- Files: `test/integration/game/round_end_test.gd`

### Step 10: Full regression pass
- [x] Run the full GUT suite headlessly. Confirmed `AnimationPlayer.animation_finished` does fire under headless, but `AnimationPlayer`'s idle-process-driven playback runs far slower than wall-clock time under `--headless` (a 0.2s animation observed taking multiple real seconds) — unlike `Tween`-based animation (`Enemy`'s fade), which completes promptly. All fade-completion tests (Step 8/9) await the `animation_finished` signal directly rather than a fixed `wait_seconds` duration, which is correct regardless of headless playback speed. To avoid this leak vector, `GameEvents.paused`/`resumed` signals were added (decoupling pause *intent* from the real `SceneTree.paused` toggle, which `Game` alone still performs) so tests can assert intent without ever setting the real paused flag — this fully resolved the anticipated `get_tree().paused` leak risk.
  Found a real, pre-existing, previously-latent test-isolation gap, newly exposed rather than caused by this feature: `round_end_test.gd` is the first test under `test/integration/game/` (which sorts alphabetically before `test/integration/inventory/`) to instance the real `game.tscn`, whose `World` emits `GameEvents.world_size_changed` — a `BehaviorSubject` that replays its last cached value to every later subscriber, including any `Player` constructed by a later test. `item_pickup_test.gd`'s hardcoded coordinates (`Vector2(3000, 2000)`, etc.) fall outside `World`'s default `1600x1200` bounds, so `Player._physics_process()`'s position clamp yanks the test's player away from its pickup once that cached value has been set by an earlier test in the same run — intermittently, `test_walking_into_pickup_with_empty_slot_equips_and_frees_it` fails in a full-suite headless run (passes standalone, and passes in the Godot editor's own GUT panel). Per user decision, this is left undisturbed and unfixed here: the real fix is a future "initialize the world for a new round" feature that ensures `world_size_changed` is (re-)emitted deterministically per round, which this feature's scope should not preempt or paper over with unrelated test-coordinate changes.
- Files: `components/events/game_events.gd`, `scenes/game.gd` (`paused`/`resumed` signals, no test files changed to work around the `world_size_changed` gap)

### Step 11: Manual verification
- [x] Launched the game and confirmed by the user: player stops moving and fades out, all enemies/projectiles/activities visibly freeze, the summary screen appears with a plausible `mm:ss` time, both buttons are clickable, "Retry" produces the same enemy/item layout as before death, and "New Seed" produces a visibly different layout.

## Risks & Mitigations
- Risk: this is the project's first use of `AnimationPlayer`, so it's unconfirmed whether `animation_finished` fires reliably/promptly under GUT's `--headless` test runner (this codebase's existing precedent for "unreliable under headless" is input simulation, per `InventoryDropInput`'s tests — a different subsystem, but a reason for caution here too). Mitigation: Step 10 explicitly calls for verifying this early, with a documented fallback (`wait_seconds` covering the animation's authored length) if `animation_finished` proves flaky headless.
- Risk: `GameEvents.round_ended` as a `BehaviorSubject` would replay "round ended" to the very next round's fresh subscriber, immediately re-freezing/re-showing the summary screen on every new round. Mitigation: use a plain `signal` instead (see Architecture Decisions) — caught during planning, not left to be discovered as a live bug.
- Risk: this project's test suite has no existing pattern for asserting on the effects of `get_tree().reload_current_scene()` (GUT's own test runner owns the actual "main scene" during a run, not `game.tscn`) — Steps 9's reload-dependent tests may only be able to verify up to "the right value was staged in `GameEvents.next_level_seed`" rather than a true end-to-end reload. Mitigation: Step 7's `ActivityManager`-level unit test independently proves the consuming side (that a staged seed is honored on `_ready()`), so the seed-carry-through logic is fully covered even if the integration test can't exercise a literal reload; the reload call itself (`get_tree().reload_current_scene()`) is a single, well-documented built-in Godot method with no project-specific logic in it, so the risk of it silently misbehaving is low even without a dedicated test.
- Risk: a test that sets `get_tree().paused = true` (directly or via triggering `round_ended`) and doesn't reset it before the test ends will leak paused state into whichever test GUT runs next, causing confusing, hard-to-diagnose failures in unrelated physics/movement tests. Mitigation: Step 10 calls this out explicitly as a regression-pass focus, and Step 8/9's new test files should add `func after_each() -> void: get_tree().paused = false` defensively.
- Risk: `GameEvents.next_level_seed` is shared autoload state, so any test that sets it without resetting afterward could leak into unrelated `ActivityManager`-instancing tests (existing or future) and cause a non-zero seed to be silently reused where a fresh random one was expected. Mitigation: Step 7 explicitly calls for resetting `GameEvents.next_level_seed = 0` in test teardown.
- Risk: `Player._on_died()` needs to find `Game` via `get_tree().get_first_node_in_group("game")` to read elapsed time, but standalone-instanced `Player` (as most existing weapon/inventory tests do via `WeaponTestHelpers.make_player()`) has no `Game` ancestor. Mitigation: Step 3 explicitly designs for a "no Game found → pass 0.0" fallback, verified by its own test (Step 8's fourth test), so existing standalone-`Player` tests remain unaffected and this feature's own tests don't require a full `Game` scene just to exercise the death sequence.

## Estimated Complexity
Medium — the death-sequence mechanics (Steps 1-2) are conceptually a straightforward mirror of `Enemy`'s existing pattern, though Step 1 also introduces this project's first `AnimationPlayer` usage (a new mechanism, even if the visual result is simple). The rest of the complexity is concentrated in Steps 3-6: this is also the project's first use of `get_tree().paused`, its first `Control`-based UI, and its first scene-reload/restart flow, so each of those has no existing convention to lean on and needed a deliberate design decision (plain signal vs. `BehaviorSubject`, `PROCESS_MODE_ALWAYS`, seed carry-through via a bare autoload field) rather than a mechanical copy of prior work. Testing both the animation-completion signal and the reload flow are inherently less certain under GUT (Steps 9-10's caveats), which is a testing-infrastructure unknown rather than a feature-complexity one.
