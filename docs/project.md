# Project: HopOnHero

## Mission
A casual top-down dodge/auto-shooter (in the vein of Archero) with tower defense elements. The player navigates a 2D arena avoiding or outmaneuvering enemies while combat and enemy waves layer in tower-defense-style strategy.

## Tech Stack
- Language: GDScript (Godot 4.7)
- Framework: Godot Engine 4.7 (Mobile rendering method)
- Build tool: Godot Editor / project.godot
- Godot executable (this machine): `E:\Tools\Godot_v4.7.1-stable_win64.exe`
- Database: none
- ORM: none
- Migrations: none
- Messaging: none
- Testing: GUT (Gut Unit Test) — Godot addon at `addons/gut/`
- Other: Jolt Physics (3D physics engine, enabled even though gameplay is currently 2D)

## Architecture
Component/behavior-based design built on Godot's node and Resource system.

- Entities are `CharacterBody2D` scenes (`scenes/player/player.tscn`, `scenes/enemy/enemy.tscn`) driven by attached scripts.
- Movement logic is factored out into `MovementBehavior` Resources (strategy pattern) rather than being hardcoded per entity: [movement_behavior.gd](components/movement/movement_behavior.gd) defines the base class with `get_velocity(position)` and `is_finished(position)`, and [target_movement_behavior.gd](components/movement/target_movement_behavior.gd) implements a concrete "move toward target" behavior.
- All entities hold a single `@export var movement_behavior: MovementBehavior` and delegate velocity calculation to it each physics frame, keeping the node script thin (player input handling lives in [input_movement_behavior.gd](components/movement/input_movement_behavior.gd)). [movement_stack.gd](components/movement/movement_stack.gd) is itself a `MovementBehavior` — an ordered push/pop stack of other `MovementBehavior`s that polls each one's `is_finished(position)` and permanently pops finished ones off the top, falling through to the behavior below — so any entity can be given layered/temporary-override movement through the same single field, with no separate type needed. [enemy.gd](scenes/enemy/enemy.gd) always uses a `MovementStack` in practice and exposes a typed `movement_stack` getter (`movement_behavior as MovementStack`) for its own internal use (e.g. a future decision engine pushing/popping temporary overrides); see Architecture Decisions below.
- Reusable behaviors live under `components/<category>/`, e.g. `components/movement/`. Follow this convention for future component categories (e.g. `components/combat/`, `components/ai/`).
- `scenes/world/world.tscn` is self-contained: it owns the `TileMapLayer` and an exported `world_size: Vector2`, but does not instance `Player` or `Enemy`. `scenes/game.tscn` is the project's main scene and the composition root — it instances `World`, `Player`, and `Enemy` together, including `scenes/camera/camera.tscn` (a standalone, reusable `Camera2D` scene) as a child of `Player`.
- Cross-cutting game-wide state is broadcast via the `GameEvents` autoload (`components/events/game_events.gd`), where each event is a `BehaviorSubject` (`components/events/behavior_subject.gd`) rather than a plain Godot `signal` — see Architecture Decisions below.

## Conventions
- Package/folder naming: lowercase snake_case for files and folders (`movement_behavior.gd`, `components/movement/`).
- Class naming: PascalCase via `class_name` (e.g. `MovementBehavior`, `TargetMovementBehavior`).
- Reusable, swappable logic (movement, and future AI/combat/etc.) should be extracted into `Resource`-based behavior scripts under `components/<category>/`, configured via `@export`, rather than hardcoded into entity scripts.
- Entity/scene-owning files (a scene paired with its root script) live under `scenes/<entity>/`, e.g. `scenes/player/`, `scenes/enemy/`, `scenes/world/`, `scenes/camera/` — mirroring the `components/<category>/` convention. Follow this for future entities (towers, bosses, projectiles). `scenes/game.tscn` (the main scene) is the composition root and lives directly under `scenes/`, not in its own subfolder.
- Tunable values (speed, targets, thresholds) are exposed via `@export` for designer/editor tuning rather than hardcoded constants buried in logic.
- No centralized error handler, REST API, or auth — not applicable to this client-side game project.
- Automated tests use GUT (`addons/gut/`). Test scripts extend `GutTest` and use a `*_test.gd` filename suffix (not GUT's default `test_*` prefix), configured via `.gutconfig.json` at the project root. Pure-logic tests with no scene-tree/physics dependency live under `test/unit/<category>/` mirroring `components/<category>/`; tests that need a live scene tree or physics (collision, `Area2D`, `Timer`) live under `test/integration/<category>/`.

## Features
- **Player Input Movement Behavior**: player movement is driven by an `InputMovementBehavior` Resource (reads `Input.get_vector` and scales by speed) instead of inline input handling in `player.gd`, aligning it with the same component pattern already used by enemies (`docs/specs-archive/202608051109-player-input-movement-behavior/`)
- **Configurable World Bounds with Camera Follow**: world size is configurable via `World.world_size` and can be larger than the screen; a reusable `camera.tscn` follows the player and clamps its view to the world's edges, and the player's own position is likewise clamped so they can never leave the playable area (`docs/specs-archive/202608051256-configurable-world-bounds-with-camera-follow/`)
- **Reorganize Scene Files into scenes/**: entity scenes and their root scripts (player, enemy, world, camera) moved from the project root into `scenes/<entity>/`, and the main scene moved to `scenes/game.tscn`, establishing a convention that mirrors `components/<category>/` (`docs/specs-archive/202608051325-reorganize-scene-files-into-scenes/`)
- **Seeded Activity Scheduler with Boss Monster Activity**: a new `ActivityManager` node periodically triggers randomly-selected `Activity` resources (currently just `BossActivity`, which spawns a boss `Enemy` at a random position with a random `TargetMovementBehavior` target) at intervals determined by the activity that just ran, with all randomness seeded from a single `level_seed` so a run can be replayed deterministically (`docs/specs-archive/202608051831-seeded-activity-scheduler-with-boss-monster-activity/`)
- **Status Scene with Health and Shield Components**: a new reusable `Status` scene, instanced as a child of `Player`/`Enemy`, holds ordered `StatusComponent` children (`HealthComponent`, `ShieldComponent`) that each get a chance to intercept/reduce an incoming `StatusEvent` (e.g. physical damage) in scene-tree order before it reaches the next component, with a `HealthBar` UI node visually reflecting current health (`docs/specs-archive/202608052127-status-scene-with-health-and-shield-components/`)
- **Unit Tests for Existing Pure-Logic Components**: added GUT unit test coverage for the deterministic, scene-tree-independent logic across movement behaviors, `BehaviorSubject`, the status/health/shield pipeline, and `BossActivity`'s reachable-distance math, establishing the `test/unit/<category>/*_test.gd` convention; also fixed two pre-existing bugs surfaced by the new tests (`HealthComponent.died` re-firing after death, and both `HealthComponent`/`ShieldComponent` emitting a spurious `value_changed` when rounded damage was `0`) (`docs/specs-archive/202608052206-unit-tests-for-existing-pure-logic-components/`)
- **Weapon System with Melee and Ranged Triggers**: a new `WeaponSystem` scene (instanced as a child of `Player`/`Enemy`, mirroring `Status`) folds over ordered `WeaponComponent` children (`modify_damage(current_damage)`) to compute total damage; a separate, swappable `WeaponTrigger` decides when to fire — `Enemy` uses `MeleeContactWeaponTrigger` (fires on physical contact via a new `HitArea`), `Player` uses `TimerWeaponTrigger` (fires on an interval, aims at the nearest enemy, spawns a `Projectile` carrying pre-computed damage). Introduces this project's first collision layers (`player`/`enemy`/`projectile`) and `Area2D`-based hit detection, plus a new `test/integration/` GUT test directory for scene/physics-dependent tests (`docs/specs-archive/202608052333-weapon-system-with-melee-and-ranged-triggers/`)
- **Enemy Death Sequence (Stop, Disable, Fade, Free)**: when an `Enemy`'s `HealthComponent` emits `died`, the enemy now stops moving (swaps to a base `MovementBehavior`), disables its `HitArea` so it can no longer deal contact damage, fades out over a tunable `death_fade_duration` (default 1s, via Godot's `create_tween()`), then frees itself — closing the loop opened by the Weapon System feature so damage can now actually and visibly kill an enemy (`docs/specs-archive/202608061748-enemy-death-sequence-stop-disable-fade-free/`)
- **Movement Behavior Stack with Chase-Player Fallback**: `Enemy` now drives movement through a `MovementStack` (an ordered push/pop stack of `MovementBehavior`s) instead of a single behavior slot; `BossActivity` builds each spawn's stack with a new `ChasePlayerMovementBehavior` at the bottom and the existing `TargetMovementBehavior` on top, so an enemy walks to its randomly-assigned destination first, then permanently falls through to chasing the player once it arrives (`docs/specs-archive/202608062336-movement-behavior-stack-with-chase-player-fallback/`)
- **Player Inventory with Passive Item Slots**: `Player` gains a 3-slot `Inventory` (a `Node`, pure `Array[Item]` state) holding `Item` `Resource`s that grant passive `WeaponComponent`s while equipped — `WeaponComponent` was migrated from `Node` to `Resource` to make this possible, and a new `InventoryWeaponComponent` folds each equipped item's components into `WeaponSystem`'s damage total at read time; items spawn on the ground via a new `ItemDropActivity` and are auto-picked-up on contact, or manually dropped via number keys. A later refinement added `Item.icon`, a `Sprite2D`-based pickup visual, and a screen-anchored `InventoryDisplay` HUD reflecting live inventory contents via a new `Inventory.slots_changed` signal (`docs/specs-archive/202608080712-player-inventory-with-passive-item-slots/`)

## Architecture Decisions

| Date | Decision | Rationale | Feature |
|------|----------|-----------|---------|
| 2026-08-05 | Cross-cutting game-wide events (starting with `world_size_changed`) are broadcast via a `GameEvents` autoload where each event is a `BehaviorSubject` (RxJS-style: caches its last value, replays it immediately to new subscribers) rather than a plain Godot `signal`. | A plain `signal` only reaches listeners connected before it fires; this silently breaks for anything that starts listening later (e.g. a boss/tower spawned mid-game, or a camera reparented after the fact), which is a scenario this project's tower-defense/wave direction and deferred camera-retargeting plans both anticipate. | [Configurable World Bounds with Camera Follow](docs/specs-archive/202608051256-configurable-world-bounds-with-camera-follow/) |
| 2026-08-05 | Any system needing deterministic, replayable randomness (starting with the activity scheduler) must seed a single `RandomNumberGenerator` from one master seed and thread it explicitly through every call site that needs randomness, rather than using per-component or global RNG state. | Global `randi()`/`randf()` calls aren't independently seedable per-instance, so mixing them into activity logic would silently break seed-replayability; threading one seeded RNG through explicit parameters makes the determinism boundary visible and enforceable. | [Seeded Activity Scheduler with Boss Monster Activity](docs/specs-archive/202608051831-seeded-activity-scheduler-with-boss-monster-activity/) |
| 2026-08-05 | Added `GameEvents.world_loaded`, a new `BehaviorSubject` that fires once when the world is fully instanced, as a distinct "readiness" signal separate from `world_size_changed` (which may fire again later, e.g. if a future activity resizes the world). | Systems that must not act before the world exists (e.g. the activity scheduler) need a one-time "everything is ready" signal; reusing `world_size_changed` for this would conflate a value-change event with a lifecycle event and break if world size changes post-load. | [Seeded Activity Scheduler with Boss Monster Activity](docs/specs-archive/202608051831-seeded-activity-scheduler-with-boss-monster-activity/) |
| 2026-08-05 | `StatusComponent` (and its subclasses `HealthComponent`/`ShieldComponent`) is `Node`-based, not `Resource`-based like `MovementBehavior`/`Activity`. | The interception pipeline's ordering mechanism is the position of sibling nodes in the scene tree itself, which only actual child `Node`s can express (a `Resource` array can't be reordered by dragging in the scene tree editor the same way). | [Status Scene with Health and Shield Components](docs/specs-archive/202608052127-status-scene-with-health-and-shield-components/) |
| 2026-08-05 | Presentation-only scenes (a visual with no independent logic beyond reflecting state, e.g. `HealthBar`) belong under `scenes/<name>/`, not `components/<category>/`, even when conceptually paired with a behavior component. | Keeps the presentation/behavior split clean: `components/<category>/` is reserved for reusable logic pieces, while `scenes/` holds anything that owns its own visual scene tree, regardless of how tightly it's paired with a specific component. | [Status Scene with Health and Shield Components](docs/specs-archive/202608052127-status-scene-with-health-and-shield-components/) |
| 2026-08-05 | Test files live under `test/unit/<category>/`, mirroring `components/<category>/`, using a `*_test.gd` filename suffix rather than GUT's default `test_*` prefix, configured via a project-root `.gutconfig.json`. | Keeps test file naming consistent with the project's existing snake_case suffix convention and makes it obvious where a new component's test belongs, without requiring CLI flags to invoke GUT headlessly every time. | [Unit Tests for Existing Pure-Logic Components](docs/specs-archive/202608052206-unit-tests-for-existing-pure-logic-components/) |
| 2026-08-05 | `WeaponComponent`/`WeaponSystem` fold over children (`modify_damage(current_damage)`, threading the running total through each), not an independent sum. | Enables future order-dependent components (e.g. a damage multiplier) to transform the total rather than being limited to flat additive contributions, mirroring `StatusComponent`'s ordered-pipeline shape. | [Weapon System with Melee and Ranged Triggers](docs/specs-archive/202608052333-weapon-system-with-melee-and-ranged-triggers/) |
| 2026-08-05 | A weapon's trigger mechanism (`WeaponTrigger` — when/how it fires) is a separate, swappable piece from its damage calculation (`WeaponComponent`/`WeaponSystem`), implemented as a `Node` (not a `Resource` like `MovementBehavior`/`Activity`). | Lets `Enemy` (melee-on-contact) and `Player` (timer + projectile) share the same damage-calculation code while differing only in firing condition; `Node` was required (not `Resource`) because a trigger owns runtime state (a `Timer` child, a signal connection) that needs its own node lifecycle. | [Weapon System with Melee and Ranged Triggers](docs/specs-archive/202608052333-weapon-system-with-melee-and-ranged-triggers/) |
| 2026-08-05 | Collision-layer identity (`player`/`enemy`) must be set on the physical `CharacterBody2D` itself, not only on a separate detection `Area2D` child. | `Area2D.body_entered` only fires for bodies whose own `collision_layer` matches the Area2D's `collision_mask` — a real bug this feature's integration tests caught, where only the `HitArea` child (not `Player`/`Enemy` itself) carried the identity layer, so melee contact silently never fired. | [Weapon System with Melee and Ranged Triggers](docs/specs-archive/202608052333-weapon-system-with-melee-and-ranged-triggers/) |
| 2026-08-06 | `MovementBehavior` completion is signaled via a polled `is_finished(position)` method, not a `finished` signal. | A signal risks an arrival race — a behavior already past its threshold when pushed onto a `MovementStack` (e.g. spawn position already within `TargetMovementBehavior`'s target radius) would never fire since nothing was connected in time; `MovementStack` already polls every physics frame regardless, so a signal would add connect/disconnect bookkeeping for no benefit. | [Movement Behavior Stack with Chase-Player Fallback](docs/specs-archive/202608062336-movement-behavior-stack-with-chase-player-fallback/) |
| 2026-08-06 | `MovementStack` (an ordered push/pop stack of `MovementBehavior`s that pops finished behaviors and falls through to the one below) is itself a `MovementBehavior`, not a separate type alongside it. `Enemy`/`Player` both keep a single `@export var movement_behavior: MovementBehavior`; `Enemy` additionally exposes a `movement_stack` getter (`movement_behavior as MovementStack`) for its own internal push/pop use. | Keeps every entity's movement field uniform (`movement_behavior` everywhere) instead of `Enemy` and `Player` diverging onto different field types/shapes; establishes the general mechanism for future temporary movement overrides (knockback, stun, charm) to be pushed on top of an entity's normal movement and later popped to restore it, rather than solving "chase then wander" as a one-off special case. | [Movement Behavior Stack with Chase-Player Fallback](docs/specs-archive/202608062336-movement-behavior-stack-with-chase-player-fallback/) |
| 2026-08-06 | A `Resource` script cannot `@export` a `Node`-derived type in Godot 4.7 — doing so causes `Parse Error: Could not resolve external class member` at compile time. | Discovered while building `ChasePlayerMovementBehavior.player`; any future `Resource`-based component needing an injected node reference must use a plain, non-exported `var` set by whoever constructs it, not `@export`. | [Movement Behavior Stack with Chase-Player Fallback](docs/specs-archive/202608062336-movement-behavior-stack-with-chase-player-fallback/) |
| 2026-08-07 | `WeaponComponent` migrated from `Node` to `Resource`, folding over `WeaponSystem.components: Array[WeaponComponent]` instead of scene-tree children. | Reverses the prior `Node`-based choice specifically for `WeaponComponent` (not `WeaponTrigger`, which stays a `Node`): items are meant to be constructed procedurally in code, and a `Resource`-based `Item` can only hold `WeaponComponent`s directly (no scene/node instantiation) if `WeaponComponent` is itself a `Resource`. | [Player Inventory with Passive Item Slots](docs/specs-archive/202608080712-player-inventory-with-passive-item-slots/) |
| 2026-08-08 | Screen-anchored HUD elements (e.g. `InventoryDisplay`) must be instanced under a `CanvasLayer`, never as a child of `Camera2D` or any other world-space node. | A node parented under `Camera2D` inherits the camera's raw, unclamped transform — once the camera itself gets clamped to the world's edges (`Camera2D.limit_*`), a child's on-screen position visibly drifts from where it should sit. A `CanvasLayer` renders in fixed screen space regardless of camera transform, zoom, or clamping, which is what any future HUD element needs. | [Player Inventory with Passive Item Slots](docs/specs-archive/202608080712-player-inventory-with-passive-item-slots/) |
| 2026-08-08 | Purely cosmetic randomness (e.g. the scatter direction when a dropped item is thrown to the ground) is exempt from the project's seeded-RNG-determinism rule and may use Godot's global `randf()`/`randf_range()` directly. | The existing rule (2026-08-05) exists to keep gameplay/replay outcomes deterministic; visual-only variance with no effect on gameplay state doesn't need to participate in that guarantee, and forcing every call site to thread a seeded RNG regardless of whether it affects outcomes would be needless ceremony. | [Player Inventory with Passive Item Slots](docs/specs-archive/202608080712-player-inventory-with-passive-item-slots/) |
